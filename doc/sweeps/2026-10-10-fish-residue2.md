# Fred Fish mass run - Phase 237d: residue II and run time

Generated by `python3 -m rdd massrun report` (Phase 232, 237b-d).

9943 executables from the Fred Fish disks, each run without input on lxa (v0.11.77) and on AmigaOS 3.1
(reference instances 0-19; the batches of the lxa-only rows re-run in 237d).

Run time (237d): lxaprobe's `WAIT_EXIT 6000` polls 300 times with `Delay(1)`, and a `Delay(1)` takes two
ticks on AmigaOS 3.1 (probe `dos/delayticks`; lxa's Delay() now does the same), so programs run about
12 emulated seconds on the reference (`C:Wait 12` returns within it, `Wait 13` does not).  lxa's budget is
now 600 frames.

Environment (237d): the reference boots a fresh SYS: for every batch of 25 programs (in crawl order) and
runs them one after the other as `LXAREF:p/<id>/<name>`, each from its own copy of its drawer.  The lxa
side now does the same: one fresh copy of its system directory per batch (without the third-party
libraries lxa ships for the app corpus), the batch's programs in order, each from a fresh copy of its
drawer on a volume `LXAREF:`.  What an earlier program of a batch left on disk is there for the later
ones on both sides; what it left in memory (a library it opened, a daemon) only on the reference: such
programs are listed apart (`ENVIRONMENT_DEPENDENT`), as are programs that read uninitialised memory or
depend on the memory map (`MEMORY_DEPENDENT`) and programs that finish sooner than the reference
(`FINISHED_SOONER`); every entry was checked.

Gate (roadmap Phase 237d): lxa-only hangs and missing windows <= 40 - **met: 68 -> 52 -> 32**; no lxa-only
crash class with 2 or more programs - **met** (largest class 1); the `cluster2-exit` ignore region -
**gone**.

## Memory-dependent programs

Their outcome depends on the bytes of the Kickstart ROM or low memory (`MEMORY_DEPENDENT` in massrun.py).

- fish-0099/A-Render/programs/LATHE (lxa crash, 3.1 hang): parses its stdin buffer (AllocMem(1032) without MEMF_CLEAR) although Read() returned 0 at end of file: the answers are whatever the memory held (Phase 237d)
- fish-0363/WO/wo1.0d (lxa crash, 3.1 window): reads IntuitionBase->ActiveScreen through a NULL IntuitionBase (Kickstart code via the vector table, Phase 237)
- fish-0365/Password/loop (lxa crash, 3.1 window): its VTBeep task starts with A4 = 0 (as on 3.1, probe exec/taskregs) and compares its stack pointer with the vector at 744(A4): on the reference the stack is in fast RAM above the ROM, on lxa below it, so lxa takes the stack-overflow path (memory map, Phase 240)
